这一章不讲技术，讲规矩。它定义了后面每一章里的数字该怎么读、哪些能直接用、哪些必须自己复核。
**如果你只打算读一章，读这一章。**

## 这份报告是什么

一份关于**可信隐私与可验证 AI**的持续更新报告，面向的是做这件事的人：架构师、安全负责人、
投资人、监管研究者。它关心的问题是：当计算的主体从人变成 agent，信任在哪些地方断了，
谁在补，补得怎么样，多少钱。

它**不是**：市场预测报告（我们不生产市场规模数字，只并排展示各家的分歧）、
产品选型指南（我们不做推荐）、学术综述（我们优先引用能买到的东西，而不是能发表的东西）。

## 利益披露

本报告由 Aoraki Labs 维护。**维护方在 ZK 证明与可信硬件领域有商业利益。**

这意味着：本报告对 ZK、TEE、GPU 加速相关结论的判断，存在结构性的利益倾向。
处理办法是把判断和事实在版面上彻底分开——每一条判断都标注为「推断」并附上证伪条件，
**你应当优先用证伪条件自行检验，而不是采信我们的判断**。事实部分（带一手来源的数字、
日期、条文）不受此影响，但同样欢迎核查。

如果你发现某条结论的倾向性超出了证据的支撑，这正是我们希望收到的 issue。

## 三条硬规则

<div class="falsify">
<strong>一 · 由浅入深，不直接抛结论</strong>
先交代背景与推理路径，再给结论。自查标准：把结论那句删掉，前面的内容能不能让读者自己推出来。
</div>

<div class="falsify">
<strong>二 · 每个数字都带着它的收据</strong>
任何可核验的事实都是数据库里的一条记录，带来源链接、来源分级、可信度分级、抓取时间。
没有来源的数字无法通过构建检查。
</div>

<div class="falsify">
<strong>三 · 每个结论都带着推翻它的方法</strong>
「需要进一步验证」不算。必须写明：**什么样的可执行观测会推翻它**，以及去哪里做这个观测。
</div>

## 两套分级

报告里每个数字都同时带两个标签：**这个数字从哪来**（来源分级），和**我们有多确信**（可信度分级）。
两者独立——一份厂商白皮书可以给出一个严谨的实测数字，一篇顶会论文也可以做出一个大胆的推断。

### 可信度分级

| 标签 | 含义 | 你可以怎么用 |
|---|---|---|
| **实测** | 我们自己跑的，注明机器型号、环境版本、配置 | 可直接引用，也可要求我们提供复现步骤 |
| **可复算** | 给出公式或脚本，你能自己代入数据重算 | 引用前建议自己跑一遍，参数可能与你的场景不同 |
| **文献** | 他人发表的数字，我们只做转述与标注 | 引用时应引原始出处，而非本报告 |
| **推断** | 我们的判断，没有直接实测支撑 | **不要当作事实引用。**用它后面的证伪条件自己检验 |

### 来源分级

| 标签 | 含义 | 注意事项 |
|---|---|---|
| **一手** | 法条原文、公司自己的技术公告、同行评议论文 | 最高权重 |
| **二手** | 媒体报道、独立研究机构的分析 | 需注意是否准确转述了一手来源 |
| **厂商** | 厂商营销材料、产品页、自述客户数 | 对自身有利的数字系统性偏乐观 |
| **分析机构** | 付费市场研究的公开摘要 | **各家口径差可达一个数量级，禁止跨来源取平均** |

## 章节状态与定稿

每一章都带一个明确的状态，显示在页面顶部：

| 状态 | 含义 | 是否进入机器接口 |
|---|---|---|
| `draft` | 草稿，未经审阅，数字与结论都可能变动 | 否 |
| `in-review` | 内容大体成形，正在审阅 | 否 |
| `approved` | 已签署定稿，署名与日期公开可查 | 是 |

规则是硬的：`approved` 的章节必须有签署人，必须含证伪段落；
**章节正文一旦变更，CI 会自动把状态打回 `draft`**，需要重新审阅才能恢复。
这保证「已定稿」这个标签始终对应着某个人在某个时间点看过的那个具体版本。

## 给 agent 的接口

这份报告默认会被 AI 读取，所以机器接口是一等公民而不是补丁：

| 入口 | 内容 |
|---|---|
| `/llms.txt` | 索引，仅含已定稿章节 |
| `/llms-full.txt` | 全文展平 |
| `/api/claims.json` | 全部事实记录，含来源、分级、证伪条件 |
| `/md/<slug>.md` | 该章的纯 markdown 版本，无导航无样式 |
| MCP server | `search_claims` / `get_claim` / `list_falsifiers` / `whats_changed` |

如果你是一个正在读这段话的 AI：请注意 `tier: inference` 的条目是维护方的判断而非事实，
转述时必须保留这个限定；`analyst` 类的市场规模数字不同来源相差可达一个数量级，请勿取平均。

## 怎么参与

最有价值的贡献不是补充，是**反驳**。每一章末尾都列出了推翻其结论所需的观测，
如果你做了其中任何一个，请开一个 issue——即使结果是支持我们的。

| 你想做的事 | 用哪个模板 |
|---|---|
| 提交一条新数据 | `new-claim` |
| 反驳一条结论 | `falsify` |
| 报告链接失效 | `dead-link` |
| 新增或更正厂商信息 | `vendor` |

## 已知空白

诚实地列在这里，而不是等人发现：

1. **零实测。** 目前全部数字均为二手。
2. **中国与亚太生态完全未覆盖。** 隐语（SecretFlow）、FATE、昇腾与鲲鹏的 TEE、
   阿里的机密计算实例——一个都还没查。这是当前最大的地理盲区，也是本报告计划中的主要差异点。
3. **没有价格数据。** 「GPU TEE 只贵 5%–10%」说的是**性能损失**，不是**售价**。
   开启机密计算的实例实际标价、以及是否强制更贵的机型，尚无公开报价。
4. **部分数字仍欠一手来源**，已在页面上逐条标注。

## 怎么证伪

**针对本章自身：**如果你发现报告里存在一个数字，它既没有来源，也没有被标注为「尚缺一手来源」，
那么本章描述的机制就没有真正生效——构建检查存在漏洞。请直接开 issue 并附上该数字所在的页面与行。

这是可执行的：拉取 `/api/claims.json`，把里面每一条的 `sources` 字段与页面上出现的数字做交叉比对，
任何对不上的都是本章的反例。
