技术清单谁都能列。决定这个赛道形状的是另外三个问题：**谁签字**、**钱从哪个科目出**、**不买会怎样**。
本章从需求侧入手，先说清楚 agent 到底新增了哪几类信任缺口，再逐个回答这三个问题。

## 本章用到的名词

不假设读者读过其他章节。完整术语表见[第 01 章](/agent-trust-stack/01-glossary/)。

| 名词 | 一句话解释 |
|---|---|
| **TEE** | CPU 或 GPU 里一块「加了锁的房间」，里面的内存是密文，连操作系统和云管理员都读不到明文 |
| **远程证明** | 芯片用出厂烧进去的私钥，签一份「我正在跑这段代码、这个配置」的报告给你 |
| **提示注入** | 把指令藏在 agent 会读到的网页、邮件或文档里，让它照着执行 |
| **zkTLS** | 不需要网站配合，就能证明「我确实从某站点拿到了这句话」，且可以只暴露其中一部分 |
| **mandate** | 一张写明「谁、允许做什么、上限多少、有效期多久」的签名文书，agent 每次行动都要带 |

## 2.1 三代信任模型：信任被搬到了哪里

先把「信任」这个词拆开。任何一次计算，都在信任三件事：**谁能看到我的数据**、**结果是不是真算出来的**、
**出了事能不能追到人**。这三件事在过去二十年一直有答案，只是答案的承担者在换。

| | SaaS 时代（2010s） | LLM API 时代（2023–2025） | Agent 时代（2025–） |
|---|---|---|---|
| **谁动我的数据** | 合同 + SOC 2 审计报告 | 合同 + 零数据保留承诺 | 合同不够了：agent 的上下文里混着多个租户、多个工具的返回值，**需要硬件级隔离与证明** |
| **结果可信吗** | 确定性代码，可重跑对账 | 不可复现，但人在看每一条输出 | 人不在回路里了，**输出直接变成行动**（下单、改配置、发邮件） |
| **出事找谁** | 用户账号 + 应用日志 | API key + 请求日志 | 一次任务跨多个服务、多个模型、多个工具端点，**身份和授权链会断** |
| **新出现的攻击面** | 凭证泄露、越权 | 越狱、数据外泄 | 提示注入 |

看最后一行。提示注入之所以是新问题，是因为 agent **把不可信的输入直接当成指令执行**——
这在 SaaS 里等价于「任何人往你数据库里写一行字，你的服务器就照着执行」。

它之所以变成生意，是因为规模。DigiCert 在 2026 年 7 月对 1,001 名 IT 与安全负责人的调查中，
<Claim id="digicert-incident-survey" /> 表示所在组织过去一年出过 AI 相关安全事件或发现过 AI 漏洞。
注意这份调查由销售同类产品的厂商发布、问卷全文未公开，所以它能说明的是「这件事已经进入采购话题」，
而不是精确的事故率。

## 2.2 六个信任缺口

与其按技术（TEE / ZK / FHE）分类，不如按**数据在一次 agent 任务里流经的位置**分类——因为买家就是这么遇到问题的。

<GapPipeline />

逐格展开：

**① 取数 / 感知.** agent 读一个网页、调一个 API。问题是它没有办法判断拿到的东西是不是真的——
页面可能是为它专门伪造的，返回值可能被中间人改过。zkTLS 解决的是这一格：
在不需要网站配合的前提下，证明某段内容确实来自某个 TLS 会话。C2PA 解决的是同一格的媒体版本，
但要注意它**不检测**合成内容，只是记录签名方关于「有没有用 AI」的自述——真实性取决于签名者是否诚实。

**② 上下文 / 记忆.** 这是唯一一个在 agent 出现之前就已经成熟的缺口。阻碍 GPU 云进入医疗、金融、国防的，
不是 DDoS 也不是凭证窃取，而是：云主机上的特权进程能在计算时直接从显存读出模型权重和推理输入。
TLS、磁盘加密、防火墙都挡不住——**数据在显存里是明文**。GPU TEE 把这一格关上了。

**③ 推理.** 跑的是不是你指定的那个模型和权重？这一格有两种答案，成本差四个数量级：
远程证明（硬件说「我加载的镜像哈希是这个」）和 zkML（密码学证明「这次计算确实按这个电路执行」）。
[第 03 章](/agent-trust-stack/03-cost/)会给出数字。

**④ 行动 / 工具.** agent 开始动手：调 API、改配置、发消息。此处的问题不是机密性而是**问责**——
这个请求是谁发的、谁授权的、权限边界在哪。这一格在 2026 年被填得最快，见 2.4。

**⑤ 支付 / 结算.** 行动涉及花钱时，问题变成「这笔钱是本人授权的吗」。
三套互相竞争的方案在打：支付网络的令牌化凭证、Google 的签名 mandate、以及稳定币原生的 x402。

**⑥ 留痕 / 举证.** 事后能不能证明它做了什么。核心难点是**日志必须是 agent 自己改不了的**——
一个能修改自己审计记录的系统，其记录没有证据价值。

<div class="falsify">
<strong>怎么证伪</strong>
把 2026 年这一批 agent 安全产品的定价页拉一遍，如果营收主要来自「密文推理」而不是「身份、网关、审计」，
那这张图的重心就画错了。可执行的检查：看 Fortanix、CrowdStrike、DigiCert、Cloudflare 四家 2026 年新发布的
agent 相关 SKU 各属于哪一类。
</div>

## 2.3 六条采购线的商业成色

把上面六个缺口换算成采购线，商业成色差别极大：

<GapTable />

最后一行值得停一下。**「推理正确性」是这张表里唯一一条找不到预算科目的线。**
它不是没有价值，而是它的价值目前只在一种场景里被真实定价：多方互不信任、且结果要被反复验证的场景。
企业买家的痛点是「云厂商会不会看我的数据」，不是「云厂商会不会偷偷换个小模型」——
因为后者他们用合同和 SLA 管，不用密码学管。

<div class="falsify">
<strong>怎么证伪</strong>
出现下面任一情况，这个判断就得改：(a) 任一主流云厂商把「推理正确性证明」做成可勾选的计费项；
(b) 某个行业监管明文要求推理过程的密码学证据；(c) 一起「模型被悄悄降级」的公开事故导致集体诉讼。
</div>

## 2.4 身份这一格，被支付网络一把拽成了事实标准

第 ④ 格在 12 个月里从无到有，路径很清楚：

- Mastercard Agent Pay <Claim id="mastercard-agent-pay-launch" />，Visa Trusted Agent Protocol <Claim id="visa-tap-launch" />。
- Cloudflare 的 Web Bot Auth <Claim id="webbotauth-production" /> 在边缘生产启用，机制是 RFC 9421 的 HTTP 消息签名加 Ed25519 密钥——
  **它不含任何新密码学**，RFC 9421 与 Ed25519 都是既有标准。
- <Claim id="webbotauth-adopters" full /> 同时，它成了上面两家支付网络的认证底座。
- <Claim id="x402-foundation" full />

这里有一个值得记住的观察：**在这个赛道里，分发渠道的价值当前高于算法的价值。**
Visa 和 Mastercard 不需要发明任何东西，他们只需要宣布「我们认这种签名」，标准就成立了。

<div class="falsify">
<strong>怎么证伪</strong>
如果到 2027 年中，带 <code>Signature-Agent</code> 头的请求仍不足 agent 流量的 1%，
说明「支付网络一宣布标准就成立」是错的，这一层仍在混战。可执行的检查：Cloudflare Radar 的
bot / agent 流量分项，以及 IETF 该工作组的 RFC 进度。
</div>

## 2.5 唯一有硬日期的买家

大部分「可信 AI」需求是软的——想做、该做、但可以推。只有一类是硬的：**不做会被罚**。

- 欧盟 AI Act 针对高风险 AI 系统的大部分义务自 <Claim id="eu-ai-act-high-risk-date" /> 起适用。
- <Claim id="eu-ai-act-logging" full />
- 罚则最高 1,500 万欧元或全球年营业额 3%，取高者。

这条线的财务映射已经被单独计量：AI 治理平台支出 <Claim id="gartner-ai-governance-spend" />，
CAGR 45.3%；Gartner 并在 2026 年 6 月把「AI 治理平台」列为独立的魔力象限品类——
也就是说，它从一个合规动作变成了一个有独立预算的软件科目。

<div class="falsify">
<strong>怎么证伪</strong>
如果 2026 年 8 月之后的一年里，欧盟没有开出任何一张针对第 12 条（日志缺失）的罚单，
且企业侧的 AI 治理平台采购增速低于预测的一半，那「合规是硬需求」这个判断就是虚的。
可执行的检查：跟踪各国市场监管机构（如爱尔兰 DPC、德国 BNetzA）2027 年 Q3 前的公开处罚记录。
</div>

## 2.6 一个比市场规模更有说服力的锚点

这个赛道的市场规模数字非常不可靠，各家基准年和口径差到数量级——[第 03 章](/agent-trust-stack/03-cost/)会把分歧并排摆出来。
这里先给一个更硬的锚点，因为它是**一次具体的采购行为**而不是一个预测：

<Claim id="apple-pcc-google-cloud" full />

一家以隐私为品牌核心的公司，愿意把最敏感的推理放到竞争对手的机房里。
它买的不是合同条款——合同它本来就能签。**它买的是远程证明。**

<div class="falsify">
<strong>怎么证伪</strong>
去读 Apple Security Research 的 <i>Expanding Private Cloud Compute</i>，
看它是否给出可被第三方独立验证的证明链：证明报告的签名者是谁、公众能不能自己验、有没有透明日志。
如果在 Google Cloud 上的部分只有 Apple 自述、没有可公开核验的 attestation，
那「Apple 买的是远程证明」就说错了——它买的其实还是合同与声誉。
</div>

## 怎么证伪（本章汇总）

| 结论 | 什么样的观测会推翻它 |
|---|---|
| agent 的新增需求主要不是密码学问题 | 2026 年 agent 安全 SKU 的营收主要来自密文推理 |
| 「推理正确性」暂无预算科目 | 云厂商把它做成计费项，或监管明文要求推理的密码学证据 |
| 分发渠道价值高于算法价值 | 2027 年中签名 agent 流量仍不足 1% |
| 合规是唯一有硬日期的买家 | 2027 年 Q3 前无任何第 12 条相关处罚 |
| Apple 买的是远程证明 | PCC 在 Google Cloud 上的部分没有可公开核验的证明链 |
